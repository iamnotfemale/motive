# WIREFRAME DESIGN BRIEF
## 문제에서 개발 인계까지 — Claude Design 요청서

> **수신자: Claude Design / 프로덕트 디자이너 역할의 디자인 에이전트**  
> 문서 버전: 1.0 · 작성일: 2026-09-18 · 공통 계약: `problem-to-handoff/v1`  
> 짝 문서: `PROJECT_BUILD_SPEC.md`  
> 제품명: **미정**. 화면에는 작은 중립적 워드마크 `Project`를 임시 사용한다.

**이 문서를 읽고 실제 서비스의 인터랙티브 와이어프레임을 만들어줘.** 랜딩페이지, 소개용 포스터, 기능 설명 슬라이드가 아니라 사용자가 매일 작업할 제품 화면이 필요하다. 핵심 흐름을 먼저 연결하고, 같은 구조에 정제된 시각 스타일을 적용해 개발 에이전트가 이어받을 수 있는 형태로 정리해줘.

새 프로젝트의 디자인을 만드는 요청이다. 기존 NOTT 화면을 복제하거나 색만 바꾸지 말아줘. 정제된 취향은 이어가되 사용자가 보는 정보와 행동의 우선순위는 달라야 한다.

---

## 0. 먼저 알아야 할 제약

### 해커톤 준비물

사용자는 기존 서비스를 이번 해커톤에 가져올 수 없다고 밝혔다. 대회 규정 전문과 디자인 사전 제작 허용 여부는 아직 확인되지 않았다. **이 요청서와 생성할 디자인의 대회 사용 가능 여부까지 확인해야 한다.** 새 이름·새 화면이라고 자격이 보장되는 것은 아니다.

NOTT의 기존 소스, CSS, Wireframe.zip, 디자인 파일, 로고, 샘플 데이터, 이미지 에셋을 가져와 고치지 않는다. 제공된 스크린샷은 취향과 구분점을 이해하기 위한 참고다. NOTT 화면 자체를 새 서비스의 앱 스크린샷으로 사용하지 않는다.

### 사실과 제안의 구분

사용자가 직접 요구한 것은 문제 작성 → 캔버스 → Evidence/Hypothesis 등 연결 → 논문·인터뷰 파일 첨부 → Markdown 편집 → 개발 에이전트용 MD 출력이다. 선호 스타일은 shadcn/ui, Aceternity UI, Notion, Vercel, Linear, NOTT, Arky다.

아래의 라이트 우선, 8종 노드, 5개 단계, 토큰·패널 크기·시나리오는 **이 제품을 위한 설계 기본안**이다. 예시 데이터를 실제 인터뷰나 통계처럼 표현하지 않는다. 문서에 없는 기능을 화면에 넣어 이미 지원하는 것처럼 보이게 하지 않는다.

## 1. 만들 제품

### 한 문장

**막연한 아이디어를 근거와 검토 질문으로 발전시키고, 선택한 해결책과 요구사항을 개발 에이전트용 Markdown으로 넘기는 캔버스형 워크스페이스.**

주 사용자는 해커톤·공모전·팀플·사이드프로젝트를 하는 대학생이다. 복잡한 기업용 지식관리 시스템처럼 보여서는 안 된다. 처음 온 사람도 “문제 하나 적으면 여기서 시작하는구나”를 알아야 한다.

### 사용자의 흐름

```text
어떤 문제를 풀고 있나요?
  ↓
짧은 문제 문서를 작성하고 시작
  ↓
Problem 카드가 놓인 넓은 캔버스
  ↓
가설 / 검토 질문 / 해결안 추가
  ↓
논문·인터뷰 파일을 카드에 드롭
  ↓
원문을 확인하고 근거 연결 승인
  ↓
해결안 채택 + 요구사항·제외 범위 결정
  ↓
인계 전 확인 → PROJECT_HANDOFF.md
```

단계는 왕복 가능하다. 처음부터 완벽한 연구 과정을 요구하지 않는다. “미검증이지만 이번 MVP에서 시도한다”도 가능한 사용자 결정이다. 대신 그 상태를 숨기지 않는다.

### 화면에서 느껴져야 하는 핵심

> **자료를 쌓는 곳이 아니라, 무엇을 만들지 판단하고 다른 사람·개발 에이전트에게 정확하게 넘기는 곳.**

## 2. 사용자의 디자인 취향

### 원하는 인상

**차분함, 정제됨, 읽기 편함, 가벼운 밀도, 정확한 인터랙션, 만드는 사람의 도구.**

“학생용”을 장난감처럼 해석하지 않는다. 귀여운 캐릭터, 성취 배지, 레벨, 원형 진행률이 아니라 도구 자체의 완성도에서 매력이 느껴져야 한다. “AI 서비스”를 보라색 그라디언트와 별 아이콘으로 표현하지 않는다.

### 레퍼런스를 섞는 방식

아래는 각 회사 디자인의 객관적 정의가 아니라 **이 프로젝트에서 참고할 요소를 고른 디자인 방향**이다.

| 레퍼런스 | 가져올 느낌 | 가져오지 않을 것 |
| --- | --- | --- |
| **shadcn/ui** | 명확한 컨트롤, 얇은 테두리, 메뉴·팝오버·탭의 일관성 | 예제 대시보드를 그대로 붙인 화면 |
| **Vercel** | 잉크색 텍스트, 정렬, 여백, 작은 경계의 정확함 | 전체 화면 검정+큰 마케팅 타이포의 무조건적 적용 |
| **Linear** | 간결한 툴바, 빠른 흐름, 선택·포커스·상태의 세밀함 | 이슈 관리용 고밀도 사이드바와 과한 업무 메타데이터 |
| **Notion** | 텍스트를 바로 쓰고 읽는 친숙함, 편집 중 방해가 적음 | 무한 문서 트리, 이모지 중심 페이지, 문서 전체 복제 |
| **Arky** | 공간에서 생각의 관계를 이해하는 감각 | 다른 제품의 캔버스 구조·인터랙션을 그대로 복제 |
| **NOTT** | 라이트 바탕, 한국어 가독성, 얇은 선, 절제된 모션 | 좌 문서/중앙 캔버스/우 AI의 상시 3열 셸 |
| **Aceternity UI** | 드롭·선택·상태 전환이 촉감 있게 느껴지는 짧은 움직임 | particles, aurora, 상시 beam, 3D tilt, 과한 glassmorphism |

Aceternity는 **모션의 참고**다. 반짝이는 컴포넌트를 많이 넣으라는 뜻이 아니다. 실제 적용은 라이선스와 구현 비용을 확인하고, 무료 기본 컴포넌트 또는 같은 원리의 작은 모션으로 충분하다. [R2]

### 기존 NOTT 스크린샷에서 읽을 것

NOTT는 좌측에 문서 계층, 가운데 큰 문서 카드와 색 있는 섹션, 우측에 상시 AI 대화가 보인다. 새 서비스에서는 다음을 바꾼다.

- 문서 트리 대신 작은 도구 레일.
- 긴 문서를 축소해 붙인 카드 대신 짧은 의미 카드.
- 파스텔 대형 섹션 대신 선과 작은 유형 배지.
- 상시 AI 채팅 대신 선택한 대상의 액션과 검토 패널.
- 기록량 대신 **열린 질문, 선택한 범위, 인계할 내용**을 강조.

스크린샷이 함께 첨부되지 않았더라도 이 설명으로 작업하되, 봤다고 주장하지 않는다.

## 3. 고정할 정보 구조

### 3.1 5개 단계

상단에만 `정의 / 탐색 / 검토 / 결정 / 인계`를 둔다. 왼쪽에 같은 단계를 다시 나열하지 않는다. 완료율 게이지가 아니라 해당 관점으로 이동하는 가벼운 탐색 컨트롤이다.

미완료 단계가 있어도 다른 단계로 이동 가능하다. 단계는 내용과 사용자의 현재 포커스에 맞춰 강조한다. `Build readiness 72%` 같은 숫자를 생성하지 않는다.

### 3.2 노드 8종

| 내부 type | 한국어 이름 | 카드에 먼저 보여줄 정보 |
| --- | --- | --- |
| `problem` | 문제 | 대상·상황·불편의 짧은 문장 |
| `hypothesis` | 가설 | 검증할 예상, 미검증/검토 상태 |
| `evidence` | 근거 | 짧은 인용·해석, 자료명·위치 |
| `challenge` | 검토 질문 | 열린 질문, 상태, 연결 대상 |
| `solution` | 해결안 | 어떻게 해결하는지, 검토/채택 표시 |
| `decision` | 결정 | 무엇을 선택했는지와 짧은 이유 |
| `requirement` | 요구사항 | 구현 행동, 범위 상태, 수용 기준 개수 |
| `note` | 메모 | 자유 메모·인사이트 |

Interview와 Paper는 자료의 종류다. 모든 인터뷰·PDF를 기본 캔버스에 또 하나의 거대한 문서 노드로 만들지 않는다. 출처 칩을 눌러 원문으로 들어간다.

처음 추가 메뉴는 `가설 추가 / 자료로 근거 찾기 / 검토 질문 추가`를 우선 노출한다. 나머지는 `다른 블록`에서 선택한다. 초보자가 ontology를 공부해야 쓰는 UI는 피한다.

### 3.3 관계 라벨

`이 문제에서 출발`, `지지`, `반대 근거`, `검토 필요`, `제안의 근거`, `채택`, `보류·기각`, `구현 범위`, `선행 필요`, `관련`을 사용한다. 내부 값은 짝 구현 명세에 정의되어 있다.

방향 화살표를 숨기지 않는다. 예를 들어 Evidence → Hypothesis는 근거가 가설을 지지한다는 뜻이다. 좌우 배치와 관계 방향이 같아야만 한다고 가정하지 않는다.

`근거 후보`는 점선, 승인한 관계는 실선으로 구분한다. 단, 점선을 누르는 것만으로 후보가 승인되지 않게 하고, 검토 패널의 명시적 `근거로 추가`를 사용한다.

## 4. 화면 셸과 레이아웃

### 기준 프레임

주 화면은 **1440×900**으로 디자인하고 **1280×800**에서의 축소 규칙을 보여준다. 데스크톱 우선이다. 모바일용 모든 캔버스 조작을 새로 설계할 필요는 없다.

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ Project  프로젝트명 ▾    정의  탐색  검토  결정  인계    저장됨  개발 인계 │
├─────────────────────────────────────────────────────────────────────────┤
│ ┌──┐                                                                    │
│ │◉ │                    Reasoning Canvas                                │
│ │▧ │                                                                    │
│ │✓ │       [문제] ─────────────── [가설]                                 │
│ │⌕ │          ↑                      ↑                                  │
│ └──┘        [근거]               [반대 근거]                             │
│                                      ↑                                  │
│                                  [검토 질문]                            │
│                                                                         │
│                    [해결안] ── [결정] ── [요구사항]                     │
│                                                                         │
│           ┌─────────────────────────────────────────────┐               │
│           │ + 블록 추가   자료 첨부   정리   − 100% +  ⛶  │               │
│           └─────────────────────────────────────────────┘               │
└─────────────────────────────────────────────────────────────────────────┘
```

이 도식은 공간 배치 설명이다. 실제 그래프의 방향·관계는 명세와 공통 예시를 따른다.

### 컴포넌트 ID와 기본 크기

| ID | 컴포넌트 | 기본값 |
| --- | --- | --- |
| CMP-01 | WorkspaceHeader | 높이 64px, 프로젝트·단계·저장·인계 |
| CMP-02 | ToolRail | 폭 48px, 좌 16px, 상단 아래 20px, 4개 주요 아이콘 |
| CMP-03 | ReasoningCanvas | 남은 공간 전체, 기본 패널 닫힘 |
| CMP-04 | SemanticNode | 폭 300px 기본, 280–320px 범위, 내용에 따라 약 132–210px |
| CMP-05 | TypedEdge | 얇은 선·방향·관계 라벨, 선택 시 라벨 강조 |
| CMP-06 | ActionDock | 높이 48px, 하단 24px, 항상 캔버스 안전 영역 안 |
| CMP-07 | ContextInspector | 선택 시 우측 약 400px, 창이 좁으면 360px |
| CMP-08 | SourceShelf | 필요할 때 하단 약 260px, 목록과 읽기 상태 |
| CMP-09 | EvidenceReviewPanel | 우측 약 440px, 원문·해석·관계·승인 |
| CMP-10 | HandoffView | 캔버스를 대체하는 점검+Markdown 화면 |
| CMP-11 | CommandMenu | Ctrl/Cmd+K, 탐색·블록 추가·선택 항목 액션 |
| CMP-12 | StatusFeedback | 저장·분석·오류·인계 변경 상태 |

레이아웃은 상시 3열이 아니다. Inspector, SourceShelf, ReviewPanel 중 큰 보조 패널은 하나만 연다. 다른 패널을 열면 현재 편집 내용을 저장하고 전환한다. 패널을 닫으면 캔버스의 원래 위치와 선택이 유지된다.

상세 편집은 비모달 Inspector를 우선한다. 원문 전문 읽기·긴 Markdown 편집을 위해 `넓게 보기`를 제공할 수 있지만 별도 문서 라이브러리로 이동하지 않는다.

1280px에서는 프로젝트명 최대 폭을 줄이고 단계 간격·보조 문구를 축약한다. 기본 글자 크기를 줄여 모든 것을 억지로 끼워 넣지 않는다. 작은 화면에서는 단계와 도구를 메뉴로 접고 상세 편집을 전체 화면으로 전환한다.

## 5. 시각 토큰

### 5.1 색 — 라이트 우선

아래는 새 디자인의 시작 토큰이다. 대비와 실제 화면을 보고 소폭 조정할 수 있으나, 레퍼런스와 다른 강한 브랜드색을 새로 발명하지 않는다.

| token | 기본값 | 용도 |
| --- | --- | --- |
| `canvas-bg` | `#F7F8FA` | 매우 옅은 회색 작업 공간 |
| `surface` | `#FFFFFF` | 노드·팝오버·패널 |
| `surface-subtle` | `#F3F4F6` | 보조 컨트롤·선택 전 배경 |
| `text-primary` | `#111827` | 제목·본문 |
| `text-secondary` | `#667085` | 보조 설명 |
| `border` | `#E5E7EB` | 기본 경계 |
| `border-strong` | `#98A2B3` | 강조 경계·구조 구분 |
| `accent` | `#2563EB` | 선택·포커스·주요 액션 |
| `accent-subtle` | `#EFF6FF` | 선택 배경 |
| `success` | `#147D4C` | 저장 성공·승인 완료 |
| `warning` | `#9A6700` | 미확인·주의 |
| `danger` | `#B42318` | 오류·반대 근거의 작은 표식 |

타입마다 카드 전체를 무지개색으로 칠하지 않는다. 유형은 아이콘·작은 배지·텍스트로 먼저 구분한다. `반대 근거`는 위험한 자료라는 뜻이 아니므로 카드 전체를 빨간 에러처럼 만들지 않는다.

선택과 분석 대상 hover가 아닌 모든 카드에 glow를 넣지 않는다. 대부분의 시간 화면은 조용해야 한다. 배경 grid는 아주 옅게 쓰거나 없애도 된다.

다크/graphite는 P1이다. 시간이 남으면 S03 한 장으로 같은 토큰 체계의 변환 예시를 보여줄 수 있지만, 라이트 핵심 흐름보다 우선하지 않는다.

### 5.2 타이포그래피

- 한국어·기본 UI: Pretendard 계열 의도. 사용 가능한 합법적 폰트와 fallback을 명시한다. 폰트 파일을 산출물에 무단 첨부하지 않는다.
- 코드·Markdown 원문: 읽기 편한 시스템 monospace.
- 화면 제목: 24px / 32px, semibold. 큰 마케팅 headline 금지.
- 노드 제목: 16px / 24px, medium 또는 semibold, 최대 2–3줄.
- UI 본문·컨트롤: 14px / 20–22px.
- 문서 본문: 16px / 26px, 한글 장문 가독성 우선.
- 역할·메타·관계 라벨: 12px / 16–18px. 중요한 정보는 더 작게 줄이지 않는다.

한국어를 좁은 버튼 안에서 부자연스럽게 끊지 않는다. 긴 프로젝트명·파일명은 ellipsis와 전체명 확인 경로를 제공한다. 카드 본문을 생략하더라도 인용·상태·출처를 모두 사라지게 하지 않는다.

### 5.3 간격과 형태

간격 단위는 4 / 8 / 12 / 16 / 24 / 32px. 버튼 기본 높이는 36px, 조밀한 툴바는 32px. 모바일 터치 경로는 더 넉넉하게 한다. 카드 안쪽 여백 16px, 패널 20–24px.

버튼 radius 8px, 카드 10px, 패널·팝오버 12px. 모든 요소를 pill로 만들지 않는다. 경계는 대체로 1px이며 그림자는 부드럽고 낮게 쓴다. heavy blur로 글자가 떠 보이는 유리 UI를 피한다.

### 5.4 카드의 정보 우선순위

```text
┌────────────────────────────────┐
│ 작은 유형 배지   H-01      ⋯   │
│                                │
│ 별도 협업 앱으로 옮기면         │
│ 제출 누락이 줄어들까?           │
│                                │
│ 미검증                         │
│ 근거 2  ·  열린 질문 1          │
└────────────────────────────────┘
```

역할 → 내용 → 상태·근거 순서다. 긴 Markdown 전문을 카드에 모두 그리지 않는다. 화면 맞춤을 누를 때 모든 노드가 너무 작아져 읽을 수 없게 된다면 선택 영역 맞춤·100% 복귀를 제공한다. 27%로 축소한 문서들이 기본 첫인상이 되어서는 안 된다.

## 6. 화면별 설계 요청

### S01 · Problem Start

**목적:** 가입·폴더·태그를 고민하기 전에 문제 문서를 적는다.

넓은 빈 화면 가운데 680–760px 정도의 작성 영역을 둔다. 질문 `어떤 문제를 풀고 있나요?`, 짧은 보조 문구 `완벽하게 정리하지 않아도 괜찮아요. 여기서 함께 구체화해요.`를 사용한다.

선택적인 제목 입력과 여러 줄 본문, `프로젝트 시작`이 중심이다. 입력 예시는 실제 플레이스홀더보다 보조 텍스트로 분리해 입력 내용과 혼동하지 않게 한다. 최근 프로젝트는 상단 메뉴나 작은 링크로만 접근한다.

필수 상태: 빈 상태, 작성 중, 입력 없음 오류, 시작·저장 중, 저장 실패. `AI가 분석 중`을 기다려야만 다음 화면에 갈 수 있는 연출은 금지한다.

### S02 · First Canvas

**목적:** 방금 적은 문서가 Problem으로 나타났다는 연속성을 만든다.

S01의 문제 문장이 Problem 카드로 이어지는 짧은 전환을 디자인한다. 생성 완료 뒤 위치를 여러 번 자동 조정하지 않는다. 근처에 `가설 추가`, `자료로 근거 찾기`, `검토 질문 추가` 세 개의 가벼운 제안을 둔다.

화면 대부분은 비어 있어도 된다. 채울 콘텐츠가 없다고 가짜 통계·큰 도움말 패널·팀원 avatar를 추가하지 않는다. `문제 다듬기`는 선택 가능한 문맥 액션이며, 원문과 AI 제안을 비교하는 상태를 포함한다.

### S03 · Reasoning Canvas

**목적:** 문제·근거·가설·결정의 관계를 실제로 읽고 조작한다.

공통 데모의 6–10개 노드를 배치한다. 카드 간 거리는 넉넉하게, 관계선은 카드 본문을 통과하지 않게 한다. 의미 그룹은 위치와 관계로 보여주고 NOTT의 큰 색 섹션 박스를 재현하지 않는다.

기본/선택/hover/키보드 focus/다중 선택/관계 선택 상태를 보여준다. 노드 hover와 선택 때만 작은 액션을 노출하되 주요 기능을 우클릭에만 숨기지 않는다.

노드별 액션 예:

- Problem: `문제 다듬기`, `가설 추가`.
- Hypothesis: `근거 연결`, `검토 질문 만들기`.
- Evidence: `원문 보기`, `다른 주장에 연결`.
- Solution: `결정 만들기`.
- Decision: `요구사항 추가`, `인계에 포함`.

상단 점검 진입은 `인계 전 확인 3개`처럼 실제 항목을 센 표현이다. 통계나 신뢰도를 임의로 그리지 않는다.

### S04 · Source Review

**목적:** 파일 첨부와 근거 확정이 다른 행동임을 이해시킨다. 이 제품의 대표 인터랙션이다.

한 화면 안에서 아래 상태가 연결되도록 설계한다.

```text
01 파일을 끌고 들어옴
02 대상 카드 위 드롭 영역 강조
03 파일 저장·텍스트 읽기
04 외부 AI 전송 동의 또는 첨부만 유지
05 근거 후보 2개 표시
06 원문 위치·인용·해석·관계 검토
07 선택한 후보만 승인
08 근거 노드와 실선 관계가 나타남
```

드롭 hover 문구는 `이 가설에 자료 첨부`. 기본 처리는 Source 추가이며 곧바로 지지 근거를 확정하지 않는다. 빈 캔버스에 놓으면 자료함에 추가하고 연결 대상을 고르게 한다.

검토 후보 예시는 다음 정보가 한눈에 보여야 한다.

```text
근거 후보                         AI 제안 · 미확정

interview-demo.md · 실제 줄 위치
“앱을 하나 더 가입해야 하면 그냥 카톡에 정리할 것 같아요.”

해석
새 계정 가입이 도입 장벽일 가능성이 있어요.
이 발언 하나를 전체 대학생에게 일반화할 수는 없어요.

연결 대상  H-01 별도 협업 앱으로 옮기면…
관계       반대 근거 ▾

원문 보기                  제외    근거로 추가
```

`원문 인용`과 `AI 해석`을 타이포·라벨로 구분한다. 사용자에게 거대한 AI 답변을 읽히지 않는다. 후보가 0개면 실패 경고 대신 `관련 근거를 찾지 못했어요. 원문에서 직접 선택할 수 있어요.`를 보여준다.

실제 PDF 화면·인터뷰 발언·줄 번호를 모사할 경우 반드시 합성 자료라고 표시한다. 임의의 논문명·연구자·효과 크기를 만들지 않는다.

### S05 · Node Detail / Markdown

**목적:** 캔버스 맥락을 잃지 않고 필요할 때 문서처럼 작성한다.

선택 시 400px Inspector가 열리고 카드의 선택이 유지된다. 상단에 유형·ID·제목·닫기, 아래에 `내용 / 연결 / 출처`. `내용`에는 `작성 / Markdown` 전환을 둔다.

가설 상세는 본문, 검증 계획, 결과 기록, 검토 상태를 표시한다. 근거 상세는 원문 인용·출처·해석·한계를 구분한다. 요구사항 상세는 사용자 행동·수용 기준·범위 상태를 보여준다. 모든 유형에 의미 없는 동일 템플릿을 강요하지 않는다.

**작성 모드는 서식 있는 본문을 직접 편집**하는 화면이고, Markdown은 원문 문법을 고치는 화면이다. 제목·목록·인용·체크리스트·링크·코드 블록 정도의 작은 서식 툴바를 보여줘. 이름만 다른 textarea 두 개로 대체하지 마. Markdown 변경이 같은 카드에 반영되는 상태를 보여준다. 본문과 별도로 문서가 생성되거나 문서 목록에 추가되는 흐름은 없다. P0에서 실제 Notion식 전체 블록·데이터베이스 엔진을 만들 것처럼 화려한 블록 조작을 설계하지 않는다. 미지원 문법이 있을 때 원문 편집으로 안전하게 유지하는 안내도 포함한다.

긴 본문은 넓게 보기가 가능하다. 저장 중·저장됨·실패는 작지만 명확해야 한다. 다른 노드로 이동해도 입력을 버리지 않는다.

### S06 · Decision & Scope

**목적:** 탐색 결과를 선택과 구현 범위로 전환한다.

해결안에서 `결정 만들기`를 누르면 선택한 해결안, 결정 이유, 기각 대안, 열린 질문·위험 인지 영역이 나온다. 기본은 초안이며 `결정 확정`은 사용자의 명시적 동작이다.

확정 후 Requirement 작성으로 자연스럽게 이어진다. `사용자가 무엇을 할 수 있어야 하나요?`, `완료됐다고 판단할 기준은 무엇인가요?`라는 친숙한 문구를 쓴다. 구현/보류/제외 구분을 보여준다.

요구사항이 생겼다고 시장 검증 완료나 개발 완료로 표시하지 않는다. “검토되지 않았지만 이번 MVP에서 시도”할 위험을 남길 수 있어야 한다.

후속 변경 상태도 그린다: `결정 이후 관련 정보 1건이 바뀌었어요` → 바뀐 근거 확인 → `검토했어요`. `AI가 틀렸다고 판단함` 같은 단정은 금지한다.

### S07 · Build Handoff

**목적:** 제품의 끝이 또 다른 문서 보관이 아니라 실제 개발 인계라는 것을 보여준다.

`개발 인계`를 누르면 캔버스 대신 점검과 Markdown 미리보기가 중심인 화면으로 전환한다. 이 화면의 좌우 분할은 괜찮다. 캔버스 기본 셸의 상시 3열 구조와는 다른 일시적 작업 화면이다.

왼쪽 약 300px: 문제·대상, 선택한 해결안, 수용 기준, 열린 질문 인지, 변경 검토, 출처 유효성, 제외 범위. 시스템 확인과 사용자가 확인해야 하는 항목을 구분한다.

오른쪽: `PROJECT_HANDOFF.md` 미리보기. 문제, 선택한 해결안, 요구사항, 결정 이유, **반대 근거**, 미검증 가설, 제외 범위, 출처가 실제 내용으로 보이게 한다.

하단 또는 우상단: `Markdown 복사`, `파일 다운로드`. 점검 미완료면 `초안으로 다운로드`를 제공한다. 모든 점검이 끝났을 때의 문구는 `인계에 필요한 정보를 확인했어요`다. `사업성 검증 완료`가 아니다.

P0에서는 `Codex 열기`, `Claude Code 실행`, `배포하기`, 실제 없는 ZIP 목록을 버튼으로 만들지 않는다. 캔버스 변경 후 미리보기 오래됨, 다운로드 완료, 복사 실패 상태도 포함한다.

### S08 · Recovery States

별도 대시보드가 아니라 해당 화면의 상태 변형으로 디자인한다.

| 상황 | 권장 문구 | 실제 다음 행동 |
| --- | --- | --- |
| 키 없음 | AI가 연결되지 않았어요. 직접 작성과 내보내기는 계속할 수 있어요. | 수동으로 계속 / 설정 안내 |
| 텍스트 없는 PDF | 이 PDF에서 읽을 텍스트를 찾지 못했어요. | 텍스트 붙여넣기 / 다른 파일 |
| 인용 미일치 | 제안된 인용을 원문에서 확인하지 못했어요. | 원문 확인 / 후보 제외 |
| 관련 근거 없음 | 연결할 근거를 찾지 못했어요. | 원문에서 직접 선택 |
| 후보 오래됨 | 분석 중 대상 내용이 바뀌었어요. | 다시 확인 / 재분석 |
| 원문 삭제 | 이 근거의 원본 자료를 찾을 수 없어요. | 자료 다시 연결 / 인계에서 상태 표시 |
| 저장 실패 | 변경 내용을 저장하지 못했어요. 이 창을 닫지 말아주세요. | 재시도 / 작성 내용 복사 |
| 일부 파일 실패 | 3개 중 1개를 읽지 못했어요. | 성공 자료 유지 / 실패 파일 확인 |
| 입력 범위 제한 | 자료 일부만 분석했어요. | 처리 구간 보기 / 다음 구간 선택 |

오류가 있어도 작성 중인 내용이 사라지지 않게 표현한다. 경고를 닫았다고 문제가 해결된 상태로 바꾸지 않는다.

## 7. 공통 예시 콘텐츠

**모든 화면은 아래 하나의 합성 시나리오로 통일한다.** 화면마다 다른 사업·논문·숫자를 사용하지 않는다. 실제 인터뷰, 연구 결과, 사용자 수, 성장률, 비용을 꾸며내지 않는다.

프로젝트명: **제출 체크룸**. 예시 프로젝트 전체에 `데모 자료` 표시를 둔다.

| ID | 유형 | 내용 |
| --- | --- | --- |
| P-01 | 문제 | 해커톤 팀은 제출 직전에 배포 주소·시연 계정·필수 첨부물을 여러 대화에서 다시 찾아야 한다. |
| H-01 | 가설 | 제출 준비를 별도 협업 앱으로 옮기면 누락이 줄어들 것이다. |
| E-01 | 근거 | “마지막에 배포 주소가 어느 메시지에 있었는지 다시 찾았어요.” |
| E-02 | 근거 | “앱을 하나 더 가입해야 하면 그냥 카톡에 정리할 것 같아요.” |
| C-01 | 검토 질문 | 팀원 전원이 새 도구에 가입해야 한다면 사용을 시작할까? |
| S-01 | 해결안 | 계정 없이 링크로 여는 제출 준비 체크리스트. |
| S-02 | 해결안 | 팀원 전원이 가입하는 별도 협업 앱. |
| D-01 | 결정 | 별도 채팅을 만들지 않고 제출 정보 확인에만 집중한다. |
| R-01 | 요구사항 | 제출 항목과 담당자를 입력·수정할 수 있다. |
| R-02 | 요구사항 | 필요한 항목이 비어 있으면 제출 전에 표시한다. |

관계는 아래를 따른다.

```text
P-01 → H-01              이 문제에서 출발
E-01 → P-01              지지
E-02 → H-01              반대 근거
C-01 → H-01              검토 필요
E-02 → S-01              제안의 근거
D-01 → S-01              채택
D-01 → S-02              보류·기각
D-01 → R-01, R-02        구현 범위
```

C-01을 위험 인지로 정리하더라도 H-01이 검증됐다는 뜻은 아니다. 별도 협업 앱 대안이 기각됐다는 사실과 연결한다. 필요하면 `체크리스트도 직접 만들 만큼 필요할까?`를 새 열린 질문으로 남기고 인계에서 포함한다.

원문 파일 `interview-demo.md`:

```markdown
# 합성 인터뷰 — 데모 전용

이 문서는 제품 화면과 테스트를 위한 가상 자료입니다.

## 참여자 A
마지막에 배포 주소가 어느 메시지에 있었는지 다시 찾았어요.

## 참여자 B
앱을 하나 더 가입해야 하면 그냥 카톡에 정리할 것 같아요.
```

PDF 장면이 필요하면 `submission-guide-demo.pdf`를 **데모용 가상 제출 안내**라고 표시하고 `배포 주소와 시연 방법을 제출하세요.` 같은 합성 텍스트만 쓴다. 원본에 없는 페이지·행 번호를 실제 출처처럼 붙이지 않는다.

요구사항 미리보기 예:

```text
R-01 · 제출 항목과 담당자 입력

사용자 행동
팀 대표가 항목을 추가하고 담당자를 수정한다.

수용 기준
• 새 항목을 추가하면 목록에 나타난다.
• 담당자를 수정하고 다시 열어도 값이 유지된다.

범위: 이번 MVP에 포함
연결된 결정: D-01
```

**중요:** 계정 없는 링크 공유는 예시 서비스가 앞으로 구현할 기능이다. 지금 디자인하는 워크스페이스 자체에 초대·공유·실시간 협업 기능을 추가하라는 요청이 아니다. 실제 P0는 1인 로컬 우선이다.

## 8. 인터랙션과 모션

### 모션의 역할

사용자가 “무엇이 바뀌었는지” 알아야 할 순간에만 움직인다. 멋진 애니메이션을 보여주기 위해 작업을 지연하지 않는다.

| 장면 | 제안 | 기본 시간 |
| --- | --- | --- |
| 버튼 hover·선택 | 배경·경계·불투명도 변화 | 100–140ms |
| 메뉴·팝오버 | 작은 opacity/scale, 위치 흔들림 없음 | 140–180ms |
| Inspector 열기 | 짧은 slide + fade | 180–220ms |
| 드롭 대상 | 한 번의 얕은 accent outline | 즉시 반응 |
| 근거 후보 등장 | 가까운 위치에서 부드럽게 나타남 | 180–240ms |
| 근거 승인 | 후보 → 확정 카드, 점선 → 실선 | 200–260ms |
| 결정 확정 | 배지 변화, 작은 확인 피드백 | 160–220ms |
| 드래그 | 포인터에 바로 붙음 | 지연·spring 없음 |

원한다면 Aceternity 계열의 미세한 border highlight를 **현재 드롭 대상 한 곳**에만 적용한다. 모든 관계선에 흐르는 빛, 무한 회전하는 별, 상시 animated beam은 사용하지 않는다.

실제 진행률을 알 수 없으면 `자료 읽는 중` 같은 indeterminate 상태로 표현한다. 거짓으로 98%까지 차오르는 progress bar를 만들지 않는다. 준비도 점수도 만들지 않는다.

`prefers-reduced-motion`에서는 공간 이동과 광택을 제거한다. 남는 텍스트·아이콘·상태로 동일한 의미를 이해할 수 있어야 한다. [R4]

### 키보드·접근성

Ctrl/Cmd+K, Tab, Enter, Escape 경로를 보여준다. 특히 승인·원문 보기·파일 첨부는 마우스 드래그나 hover 없이도 가능해야 한다. 텍스트 편집 중 Delete/Backspace를 노드 삭제로 쓰지 않는다.

Inspector는 desktop에서 비모달일 수 있고, 확인 Dialog는 모달이다. focus trap과 포커스 복귀는 역할에 맞춰 설계한다. 색만으로 지지·반대·오류를 구분하지 않는다. 본문·라벨의 대비와 focus ring을 체크한다.

## 9. 범위와 만들지 말아야 할 것

### 반드시 표현

문제 입력, 첫 캔버스, 편집 가능한 의미 카드, 자료 드롭·근거 승인, 원문과 해석 구분, Markdown, 결정·요구사항, 미확인 상태를 남기는 MD 인계.

### 디자인만 그려놓고 지원하는 척하지 않기

로그인·결제·팀원 초대·실시간 커서·음성 전사·스캔 OCR·자율 웹 검색·자동 배포·에이전트 실행·시장 검증 점수. P1 확장 아이디어가 생기면 별도 메모로만 남긴다.

### 시각적 금지 목록

- 좌 문서 트리 / 중앙 캔버스 / 우 AI 채팅을 그대로 둔 NOTT 변형.
- 서비스 화면 대신 랜딩 hero, pricing, testimonial, 고객 로고로 작업량을 채우는 것.
- 설명 가능한 근거 없는 통계·완료율·신뢰도·가짜 사용자 수.
- 네온 보라색 AI dashboard, 우주 배경, 입자, 과한 glow, 무지개 카드.
- 매 카드마다 과한 그림자·유리 배경·3D 회전.
- 빈 공간을 없애기 위한 불필요한 패널·charts·widgets.
- 읽을 수 없을 만큼 작은 문서를 여러 장 펼쳐놓은 기본 화면.
- 실제 쓰지 못할 기능 버튼으로 제품을 풍성해 보이게 하는 것.

## 10. 요청 산출물과 작업 순서

### 1단계 · 인터랙션이 연결된 와이어프레임

S01–S07을 같은 예시 데이터로 이어줘. S08은 각 화면의 변형 상태로 포함해줘. 먼저 한 가지 일관된 방향을 만들고, 서로 다른 세 가지 브랜딩 시안으로 시간을 쓰지 말아줘.

중요한 클릭은 `시작 → 가설 추가 → 파일 드롭 → 원문 보기 → 근거 승인 → Markdown 편집 → 결정 → 요구사항 → MD 인계`다. 툴에서 실제 파일 드롭·다운로드를 구현할 수 없다면 프로토타입의 모의 동작이라고 표시하고 상호작용을 재현해줘. 실제 백엔드 기능이 있다고 주장하지 마.

### 2단계 · 핵심 화면의 시각 완성

우선 S02/S03 캔버스, S04 근거 검토, S05 편집, S07 인계의 스타일을 동일한 토큰으로 완성해줘. 단순 회색 박스만이 아니라 **한국어 타이포·간격·카드 밀도·컨트롤 상태가 보이는 수준**이 필요해.

1440×900 기본과 1280×800 압축 규칙을 보여줘. 모든 화면을 어둡게 바꾸는 작업은 나중이야. 폰트와 대비는 실제 화면에서 확인해줘.

### 3단계 · 개발 인계

아래를 가능한 형식으로 정리해줘. 도구가 특정 파일 export를 지원하지 않으면 내용을 텍스트로 제공하고, 존재하지 않는 파일 링크를 만들지 마.

| 산출물 | 필요한 내용 |
| --- | --- |
| 화면·프로토타입 | `S01_problem-start`, `S02_first-canvas` 등 안정적 ID와 상호작용 |
| 컴포넌트·상태 표 | CMP-01–CMP-12, 기본/hover/focus/선택/오류/loading |
| `design-tokens.json` 또는 동등 표 | 색, 타이포, spacing, radius, shadow, motion |
| `DESIGN_HANDOFF.md` | 화면 구조·행동·컴포넌트·반응형·접근성·미정 사항 |
| 구현 참고 코드 | 도구가 제공할 때만. 새 산출물이며 사용 허용 여부 별도 확인 |
| 화면 이미지 | 가능한 경우 검수용 export. 기존 NOTT 이미지를 재사용하지 않음 |

기능 데이터 계약은 `PROJECT_BUILD_SPEC.md`를 바꾸지 않는다. 불가피한 변경 제안은 `제안 변경 / 이유 / 영향 화면`으로 따로 적고 확정된 요구처럼 적용하지 않는다.

### DESIGN_HANDOFF.md 필수 골격

```markdown
# Design Handoff

승인 전이면 '검토 대기'로 표시한다.
```

## 11. 디자인 검수 체크리스트

- 처음 5초 안에 “문제를 적고 시작하는 도구”임이 보이는가?
- Problem → 근거 검토 → 결정 → 인계가 하나의 실제 사용자 흐름으로 연결되는가?
- NOTT의 상시 3열 문서 앱과 다른 정보 구조가 명확한가?
- 파일 첨부, AI 후보, 승인된 근거를 혼동하지 않는가?
- 원문 인용과 AI 해석이 구분되고 출처 위치를 확인할 수 있는가?
- 카드 제목·상태가 기본 배율에서 읽히고 긴 전문은 별도로 편집 가능한가?
- 오른쪽에 상시 챗봇이 없고 액션이 대상의 문맥 안에 있는가?
- 결정은 사람이 확정하며 미검증·위험을 남길 수 있는가?
- 인계 문서에 반대 근거·열린 질문·제외 범위가 남는가?
- AI·저장 실패에도 사용자가 다음 행동을 알 수 있는가?
- 한국어가 자연스럽고 빈 화면·긴 제목·많은 자료에서 레이아웃이 유지되는가?
- 움직임이 상태를 설명하고 reduced-motion에서도 의미가 유지되는가?
- 실제 없는 기능·사용자·연구·정량 점수를 만들어내지 않았는가?
- 개발자가 이미지뿐 아니라 행동·상태·치수를 이해할 자료가 있는가?

## 마지막 요청

**깔끔한 문서 편집기의 편안함, 캔버스의 공간감, 개발 도구의 정확함을 한 제품 안에서 맞춰줘.**

shadcn 기반의 조용한 UI에 Aceternity의 촉감 있는 상태 전환을 조금만 더해줘. NOTT와 같은 취향은 느껴지되, 첫 화면과 작업 흐름은 분명히 새로운 제품이어야 해.

예쁜 캔버스 한 장보다 **문제를 적고, 자료를 확인하고, 결정을 남기고, 실제 개발 명세를 가져가는 경험**을 완성해줘.
